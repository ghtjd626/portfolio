# ADR-0001 — 핵심 논지 채택 + 동적 스키마를 데이터로 모델링

- **상태:** Accepted
- **날짜:** 2026-07-27
- **관련:** discovery.md, vision.md, ADR-0003(동기화 엔진), ADR-0004(모노레포)

## What — 무엇을 결정하는가

Lore의 두 기술적 척추를 확정한다:
- **논지 A — 사용자 정의 스키마:** 도메인을 하드코딩하지 않고, "기록 종류(Record Type)"를 사용자가 데이터로 정의한다.
- **논지 B — Local-first:** 데이터의 1차 사본은 사용자 기기에 있고, 오프라인에서 즉시 동작하며 서버는 동기화 원천이다.

그리고 두 논지의 충돌을 **"동적 스키마를 코드가 아니라 데이터로 모델링해 물리 스키마를 고정한다"** 로 해소하기로 한다.

## Context — 배경 / 결정 동인

- discovery의 통증: 파편화 · 소유권 부재 · 경직성.
- "거의 모든 걸 **내 입맛대로**"(→ A), "**매일 쓸** 제품 · **내 데이터 소유**"(→ B).
- 차별화는 스택이 아니라 **의도된 어려운 설계 판단**에서 나와야 한다(브리프 §4).

**충돌:** 대부분의 local-first 동기화 엔진은 스키마가 컴파일 타임에 *고정*이라 가정한다. 그러나 A는 스키마가 런타임에 사용자마다 *동적*이다. 순진하게 결합하면, 사용자가 종류를 만들 때마다 물리 테이블/마이그레이션이 생기고 동기화 엔진이 이를 못 따라간다.

## Considered Options — 검토한 선택지

동적 스키마의 저장 방식으로:

- **옵션 1 — 종류마다 물리 테이블 생성 (DDL 동적 생성).**
  각 기록 종류가 진짜 테이블. 쿼리는 자연스럽지만, 런타임 DDL은 마이그레이션·동기화·권한 관리가 지옥이 되고 local-first 엔진과 상극.
- **옵션 2 — EAV (Entity-Attribute-Value).**
  완전 유연하지만 쿼리가 조인 지옥, 타입 안전·성능 모두 취약.
- **옵션 3 — 고정 물리 스키마 + JSONB `data` + 스키마 레지스트리(채택).**
  물리 테이블은 소수 고정(`record_types`, `records`, `tags`). 종류 정의는 `record_types`의 행. 종류별 값은 `records.data`(JSONB). 검증은 FieldDef → Zod 컴파일.

## Why — 결정과 근거

**옵션 3을 택한다.**

- **동기화가 트랙터블해진다.** 동기화 엔진은 *고정된 소수의 테이블*만 다루면 되므로, 어떤 동적 스키마가 와도 물리 계층은 불변 → 논지 B와 충돌하지 않는다. (이게 결정적 근거)
- **유연성 유지.** 종류·필드는 데이터라 런타임에 자유롭게 생성/변경. 논지 A 충족.
- **타입 안전 확보 경로가 있다.** FieldDef[] → Zod 스키마로 컴파일해 런타임 검증. 물리 DDL 없이도 "구조가 있는" 데이터를 보장.
- **쿼리 가능성 확보 경로가 있다.** 자주 쓰는 필드는 JSONB 위 **생성 컬럼 + 인덱스**로 승격(핫 패스만 최적화).

EAV(옵션 2)보다 쿼리·타입이 낫고, 동적 DDL(옵션 1)보다 동기화·운영이 압도적으로 단순하다.

## How — 어떻게 적용하나

- 물리 스키마: `record_types(id, owner_id, name, fields jsonb, ...)`, `records(id, owner_id, type_id, occurred_at, title, data jsonb, updated_at, deleted_at, ...)`, `tags`.
- `packages/schema-core`: `FieldDef` 타입 + `compileToZod(fields)` — 클라·서버 공유(→ ADR-0004).
- 동일 FieldDef로 폼 렌더러·뷰 렌더러 생성.
- 핫 필드는 생성 컬럼으로 승격, 조기 벤치마크로 검증.
- soft delete(`deleted_at`) + `updated_at`/버전으로 동기화·충돌 해결 기반 마련.

## Trade-off / Consequences

- **좋은 점:** 동적 유연성과 local-first 동기화가 양립. 물리 스키마가 안정적이라 마이그레이션이 드물다. 도메인 기능이 메타 시스템의 인스턴스로 환원됨(프리셋).
- **나쁜 점 / 감수하는 비용:** JSONB 쿼리는 일반 컬럼보다 신경 써야 함(인덱싱·성능). DB 레벨의 강한 제약(외래키·체크) 대신 애플리케이션(Zod) 검증에 의존. 복잡한 관계형 질의는 제한적.

## Counterfactual — 반사실

- 만약 **local-first(B)를 포기**했다면, 동적 DDL(옵션 1)도 현실적이었을 것이다. 즉 이 결정은 "B를 지킨다"는 전제에서 정당하다.
- 만약 **사용자 정의(A)를 포기**하고 도메인을 하드코딩했다면, 평범한 CRUD 앱이 되어 차별점이 사라진다 — 그건 이 프로젝트의 존재 이유를 부정한다.
- 즉 옵션 3은 **A와 B를 동시에 지키려는 제약 하에서의 최적해**다.
